# Vitro Engineering Guide

## Product goal

Vitro is a data-profiling platform. Users authenticate into a workspace, organise data into datasets and assets, upload source files, request profiling tasks, and inspect task runs and profiling results.

The project is currently a prototype. Authentication and metadata CRUD are implemented. Task execution and several dashboard, preview, schema, and file-tree views are still placeholders; do not describe them as production profiling behavior.

## Business entities

- **User**: authenticated person with a default workspace.
- **Workspace**: tenant boundary for all metadata and operations.
- **Dataset**: workspace-scoped logical collection of assets.
- **Asset**: dataset-scoped data source with upload connector metadata.
- **File**: CSV uploaded into an asset storage prefix.
- **Task**: requested profiling operation for an asset.
- **Task run**: one execution attempt and its status, errors, and metrics.

Workspace isolation is a security invariant. Every protected read and write must verify both authentication and workspace membership; a caller-provided workspace ID alone is not authorization.

## Repository structure

```text
packages/
  frontend/  React 19, TanStack Start/Router/Query, Zustand, Zod, Tailwind, shadcn/ui
  backend/   Rust, Axum, SQLx, PostgreSQL, layered router/service/repository/model code
scripts/     Shared deterministic development scripts
```

The repository uses Bun workspaces and Turborepo. Run workflows from the repository root; package scripts are Turbo implementation details.

## Development workflow

```shell
bun install
bun run setup
bun run db:up
bun run db:migrate
bun run dev
```

Useful focused commands:

- `bun run dev:client` and `bun run dev:server`
- `bun run test:client` and `bun run test:server`
- `bun run test:e2e` for the database-backed backend flow
- `bun run lint`, `bun run format:check`, and `bun run typecheck`
- `bun run format` to write formatting
- `bun run check` before handoff
- `bun run db:down` to stop local database services

`bun run setup` is idempotent and never overwrites an existing `.env`. SQL migrations require `sqlx-cli`.

## Coding conventions

- Think before coding: state assumptions, success criteria, and material tradeoffs.
- Prefer the minimum code that solves the requested behavior; avoid speculative abstractions.
- Make surgical changes and preserve unrelated user work.
- Read a file, its caller, and shared utilities before changing it.
- Match existing names and architecture. Surface contradictory patterns instead of blending them.
- Use the model for judgment over unstructured information, not deterministic routing or transforms.
- Tests must encode business intent and meaningful failure behavior.
- Fail loudly when commands, migrations, or checks are incomplete.
- Never edit `packages/frontend/src/routeTree.gen.ts` manually; it is generated by TanStack Router.
- Frontend code uses strict TypeScript and Biome. Avoid `any` unless an external boundary makes it unavoidable.
- Backend code must pass rustfmt, Clippy with warnings denied, and `cargo check --all-targets --all-features`.
- Keep router code focused on HTTP extraction/response mapping, services on business rules, and repositories on persistence.
- Do not claim a task complete until focused tests and the broad root checks have fresh passing evidence.
